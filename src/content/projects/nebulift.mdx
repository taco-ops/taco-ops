After a clear night with a telescope, you return with hundreds of FITS files and the modest hope that a useful fraction survived. Some frames contain the target. Others contain clouds, satellite trails, tracking errors, and hot pixels. Separating them by hand is the kind of work that makes people abandon hobbies.

Nebulift is a local CLI tool for FITS image quality assessment. Computer vision handles the obvious cases. An optional ResNet18 classifier, trained on your own data, handles the ones that aren't.

# What It Does

The core workflow is a batch analysis command that processes a directory of FITS files and writes a JSON manifest:

```bash
uv run nebulift batch /path/to/raw/fits /path/to/output
```

By default that is report-only. Add `--action move` to sort files into class directories. Supply a trained model checkpoint with `--model` to layer ML classification on top of the CV pass.

Every frame gets one of three labels: `clean`, `contaminated`, or `review`. The CV pass produces a quality score based on streak detection (Hough transforms), cloud texture analysis, saturation mapping, and hot pixel counts. Scores above a configurable threshold are `clean`; scores below another threshold are `contaminated`; everything between goes to `review`.

# The Full Workflow

Batch analysis is the start. The real workflow is the loop that follows it.

After a batch run, `nebulift review` opens each manifest entry in sequence and lets you correct labels in the terminal. It doesn't display image previews yet. What it does do is produce a reviewed manifest you can actually learn from.

```bash
uv run nebulift review /path/to/output/batch_manifest.json
```

From there:

- `evaluate-manifest` compares your corrected labels against CV or model decisions and reports accuracy, a confusion matrix, and per-class F1.
- `calibrate-thresholds` sweeps clean and contaminated score thresholds across one or more reviewed manifests to find the settings that maximize macro F1 on your actual data.
- `export-curated` copies reviewed files into organized class directories for training.
- `train-from-manifest` trains a ResNet18 model from those labels.
- `register-model` stores the result in a local registry and optionally promotes it as the default, so subsequent `analyze` and `batch` runs use it automatically.

The loop is: collect, review, calibrate, train, register, repeat. Each pass produces labeled data and a model better calibrated to your telescope and site conditions.

# Training

Two training paths exist. `train-from-fits` generates CV labels automatically from a raw FITS directory and trains on those:

```bash
uv run nebulift train-from-fits /path/to/fits/session \
    --model_output models/custom_classifier.pth \
    --dataset_dir datasets/session_training \
    --epochs 50 \
    --clean_threshold 0.7 \
    --contaminated_threshold 0.3
```

`train-from-manifest` trains from labels in a reviewed manifest, using `corrected_label` where present and falling back to `decision_label` otherwise. Add `--reviewed_only` to train only from explicitly reviewed entries.

No pretrained Nebulift model ships with the repository. The classifier is only useful once you've generated enough labeled data from your own sessions to train it.

# What Is and Isn't Ready

The local FITS workflow is the primary supported path. That means: loading, CV analysis, batch sorting, interactive review, threshold calibration, curated export, and local training. That loop works.

The Kubernetes, Argo CD, and distributed training resources are present in the repository but should be treated as scaffolding. Distributed training still needs real dataset mounting, model persistence validated end-to-end, and actual cluster storage. The `k8s/` and `argocd/` directories are useful for infrastructure iteration, not production deployment.

Raspberry Pi 5 is a design target for local inference. Real-world performance figures don't exist yet.

# The Practical Use Case

Every astrophotography session produces frames that should not go into the stacking pipeline. The question is how many hours you want to spend finding them. Nebulift reduces that work by doing the deterministic part automatically and making the uncertain part visible rather than hidden.

The three-category output is the core design decision. Forcing a binary `keep/discard` on borderline frames produces confident wrong answers. Surfacing them explicitly for human review produces accurate stacks and labeled data for the next training run.
